KV-CACHE STORAGE BENCHMARKING

kvspill is now kvio bench

Davidlohr Bueso built kvspill to load-test an SSD with sustained fio patterns chosen for KV-cache offload. With his permission, those tests now complement kvio's projection, capture, attribution, and replay tools under one Apache-2.0 command.

Why kvspill existed

kvio started from application intent: calculate KV-object geometry, observe real device commands, and replay the stream. kvspill started from the device: keep an SSD busy with repeatable fio jobs and measure throughput, latency, CPU cost, and interference without a GPU or model server.

What kvio absorbed

The five workload shapes, preconditioning, fio JSON parsing, RESULT lines, and median A/B comparison came from kvspill. kvio adds one launcher, evidence labels, external JSON profiles, overridable calibrated object sizes, structured artifacts, target-only IRQ accounting, capacity-bounded regions, checked failures, hard mount/partition/holder checks, and guaranteed restoration of queue and hugepage tuning.

Run it

make kvio-test
./kvio doctor
./kvio bench --list-profiles

# WARNING: this preconditions and overwrites the selected raw namespace
sudo ./kvio bench /dev/nvmeXnY \
  --yes-really-use-device --size 8GiB --reps 3 \
  --output-dir results/baseline

sudo ./kvio bench /dev/nvmeXnY \
  --yes-really-use-device --cases restore-calibrated \
  --calibrated-block-size 32MiB --size 8GiB \
  --output-dir results/restore-32m

./kvio bench-compare results/baseline/results.jsonl \
                     results/candidate/results.jsonl

Use --profile FILE to add a sustained workload derived from a future capture. The JSON names its evidence as measured or synthetic, cites the source, and defines each fio job's operation, block size, queue depth, and worker count. The resolved profile is saved in run.json.

Raw-device contract: use only an independently verified empty, disposable namespace. The acknowledgement never bypasses mounts, partitions, holders, or capacity checks; signatures require a separate switch.

Interpretation limits

kvio bench controls object size, direction, workers, queue depth, and sequential/random shape. It does not reproduce serving arrival times, cache policy, object lifetime, or an exact captured offset sequence. Capture and replay those when fidelity is the question; use the benchmark cases when headroom and interference are the question.

The QoS case is synthetic: qos-sustain-4k does not claim that LMCache issues 4 KiB reads. It asks how badly sustained large reads delay one possible latency-sensitive neighbor. David measured this fio mix in his storage campaign, but did not derive the mix from a production serving trace. Treat it as the first interference profile, not as a universal workload.

The 7,340,032-byte default is a real calibration point. David traced LMCache 0.5.3 with vLLM 0.27.1, Qwen2.5-1.5B-Instruct, TP1, bf16, and 256-token chunks. Its size is 2 (K and V) × 28 layers × 2 KV heads × 128 values × 2 bytes × 256 tokens = 7,340,032 bytes, exactly 7 MiB. The run used four synchronous disk workers and reported 108 stores and 200 restores of that size. See the source profile. It is not a universal KV size.

Bare-metal validated: before merge, every case, the 32 MiB override, comparison, OS-disk refusal, and tuning cleanup ran on a verified-empty Samsung PM9A3 in a Latitude m4-metal-medium. Queue and hugepage values matched their pre-run state afterward. The reproduce directory records the gates and short-run evidence.
